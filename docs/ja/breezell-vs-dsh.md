# Breezell と DSH：根本的な違い

よく寄せられる質問の一つが、Breezell と DSH（deepseek-harness）は何が違うのかというものです。簡潔に言えば、両者は開発と保守のモデルで異なる優先順位を採用しています。

## クイック比較

| 項目 | DSH | Breezell |
| --- | --- | --- |
| 製品モデル | コミュニティ主導のフレームワークとエコシステム | 公式チームが中心となって保守する統合 IDE |
| 基本体験 | 基盤と選択したコミュニティ拡張を組み合わせる | 導入直後から完成した製品として利用可能 |
| 保守 | 機能や連携がコミュニティに大きく依存する場合がある | 中核機能と連携を公式に統括 |
| 拡張性 | 高い自由度と迅速な実験 | 現在はより管理され、段階的に開放 |
| 一貫性 | 拡張ごとに品質や体験が異なる可能性 | 動作、設計、リリース基準を統一 |
| セキュリティ | 各拡張の入手元、権限、実装に依存 | 公式コアをより管理された境界内で維持 |
| トレードオフ | 利用者による拡張の確認が必要 | 修正や機能追加が公式開発を待つ場合がある |

## DSH のアプローチ

DSH はコミュニティ主導のフレームワークに近く、公式プロジェクトが基盤を提供し、多くの機能、連携、プラグイン、ワークフローはコミュニティ拡張から提供される場合があります。

高い自由度、迅速な実験、細かなカスタマイズが可能な一方、利用者側の責任も大きくなります。拡張可能な開発ツール全般と同様、信頼できない、または設計の不十分な拡張は、認証情報の露出、プロンプトインジェクション、不安定な動作、破壊的操作を招く可能性があります。

実際のリスクは、コミュニティ製かどうかだけではなく、入手元、要求権限、実装品質、審査方法によって決まります。

## Breezell のアプローチ

Breezell は、公式製品としての開発、統合、保守を中心にしています。利用者が中核ワークフローを複数のプラグインから組み立てなくても、そのまま使える体験を目指しています。

これにより、製品動作、インターフェース、モデルとツールの連携、互換性テスト、セキュリティ境界、更新、サポートを一貫して調整できます。

信頼できない第三者拡張を導入しない限り、中核体験は公式に保守された環境内に保たれ、未知のコード、認証情報、プロンプトインジェクション、破壊的動作に関する不確実性を大幅に抑えられます。

::: info セキュリティ境界は絶対的な保証ではありません
第三者拡張を導入する際は、入手元、公開者、権限、評判を確認してください。
:::

## トレードオフ

公式による統括は一貫性、安定性、管理性を高める一方、開発上のボトルネックにもなります。現在の Breezell は公式リソースへの依存度が高く、一部の修正や連携はチームの対応を待つ必要があります。

コミュニティ主導のエコシステムは、より速く実験し拡大できる場合があります。Breezell は現在、予測しやすい中核体験を優先しています。

## Breezell の今後

Breezell は VS Code を基盤とし、その更新を継続的に取り込んでいます。

長期的には、明確な権限表示、分離されたセキュリティ境界、透明な配布元、安定した公式 API、第三者プラグインなしでも使える公式コアを維持しながら、コミュニティが拡張を開発・配布できる仕組みを目指します。

## 結論

> **DSH は最大限の自由を重視するコミュニティ主導フレームワークに近く、Breezell は一貫性、安定性、セキュリティ境界を重視した公式保守の完成製品を中心に、管理された形で拡張性を段階的に開放します。**
