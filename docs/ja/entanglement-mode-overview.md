# Entanglement モードの概要

> Entanglement は複雑な問題向けの因果推論強化モードです。

## 概要

Breezell の Entanglement モードは、量子アルゴリズムでも、複数のモデルを自動的に起動する協調モードでもありません。
実装では、Agent の機能、因果状態マシン、予測/介入/検証の制約、可視化パネル、収束メモリを組み合わせています。
基盤モデルを突然賢くするものではありません。複雑なタスクに含まれる仮説、証拠、実験、結論を継続的に保存し、再びモデルへ注入します。

## 1. 主な結論

Entanglement は Agent の完全な代替ではありません。複雑な問題向けの状態を持つ強化機能です。

- **ツール機能：** Entanglement は Agent のファイル、ターミナル、検索、MCP、コードインデックス機能を継承します。
- **推論の整理：** Entanglement はさらに、段階、根本原因、仮説、証拠、予測、検証、確信度を管理します。
- **実行効率：** 明確に定義されたタスクでは通常の Agent の方が速いことが多く、Entanglement ではコンテキストとトークンのオーバーヘッドが増えます。
- **適した用途：** 未知のバグ、モジュール横断の障害、実験的な検証が必要な問題には Entanglement が適しています。
- **機能の境界：** 独立した Entanglement モデル、量子コンピューティングモジュール、複数モデルの並列実行経路がデフォルトで存在するわけではありません。

## 2. 仕組み

### 1. モード選択

フロントエンドのモード一覧には `normal`、`plan`、`analyze`、`entanglement`、`agent`、`agent_teams` が含まれます。
Entanglement を選択すると、それ以降の会話ターンで因果状態の追跡が有効になります。

### 2. Agent 機能の継承

バックエンドのモード解決では `entanglement` を Agent 型に割り当てるため、ファイルツール、ターミナル、検索、MCP、コードインデックスを引き続き呼び出せます。
これが分析専用モードとの違いでもあります。Entanglement はプロジェクトを変更し、検証を実行できます。

### 3. 現在の因果状態の注入

各リクエストには現在のスレッドの因果状態が含まれ、Agent レベルのアクティブファイル、ワークスペース、ツールのコンテキストが使用されます。

### 4. 同じモデルとツールのループ

Entanglement と Agent は同じモデル機能とツール実行機能を使用します。
したがって Agent Teams と同じものではなく、デフォルトで複数の独立した AI を作成することもありません。追加のサブタスクやツール呼び出しが発生するのは、モデルが関連するツールを自発的に使用した場合だけです。

### 5. モデル応答の解析

モデルの応答後、システムは段階、根本原因、仮説、証拠、予測、検証結果を解析し、現在のスレッドに保存します。
次のターンでもこの状態が使われ、インターフェースには構造化された状態ブロックが「Causal Trace Complete」と表示されます。

### 6. 可視化とリアルタイム解析

Entanglement パネルのコンポーネント `G1` は、現在の段階、確信度、根本原因、仮説、証拠、因果グラフ、修正、検証、システムによる補正を表示します。
モデルのストリーミング出力中、フロントエンドはテキストの増加量または時間間隔に基づいて状態を再解析します。LLM 以外の出力フェーズでは、一時的な解析結果を消去します。

### 7. 収束後のメモリ

状態が高い確信度の `CONVERGE` 段階に達し、明確な根本原因が存在すると、システムは問題を `causal-case` タグ付きの Memory Bank ノードに整理します。
メモリには症状、根本原因、メカニズム、決定的な証拠、修正、因果グラフ、却下された仮説、検証結果が含まれます。

### データフロー

```text
モードメニューから Entanglement を選択
        ↓
グローバル chatMode = "entanglement" を設定
        ↓
現在のスレッドの causalState を読み込む
        ↓
標準の LLM/ツールループを維持したまま因果コンテキストを注入
        ↓
モデルが返した段階、仮説、証拠、検証結果を解析
        ↓
状態をスレッドに書き戻し、ダッシュボードを更新
        ↓
高い確信度で収束した後、causal-case メモリを書き込む
```

## 3. 因果状態マシン

### 1. 段階

| 段階 | 意味 |
| --- | --- |
| `OBSERVE` | 根本原因がまだ明確でない状態で、現象と証拠を集めます。 |
| `INTERVENE` | ツールまたは実験による検証が必要なアクションを提案します。 |
| `CONVERGE` | 根本原因、修正、検証のループを徐々に閉じます。 |
| `BACKTRACK` | 現在の仮説が却下され、推論を以前の地点へ戻す必要があります。 |

### 2. 状態フィールド

スレッドの主な状態には、`phase`、`rootCause`、`mechanism`、`confidence`、`hypotheses`、`evidenceLog`、`evidenceSummary`、`causalGraph`、`causalGraphEdges`、`counterfactual`、`fix`、`verify`、`pendingPrediction`、`turnCount`、`stuckTurns`、`corrections` が含まれます。

### 3. 仮説管理

仮説には `H1`、`H2` などの識別子を使用し、`testing`、`confirmed`、`rejected` の状態を記録します。
また、Kill Criterion、Lesson、作成ターン、最後に扱ったターンを保存し、却下済みの推論が再び採用されるのを防ぎます。

### 4. 証拠と因果グラフ

証拠は `++`、`+`、`~`、`-`、`--` の5段階に対応し、証拠の取得元ツールも記録できます。
パーサーは直近20件の詳細な証拠を保持し、それより古い内容を要約に圧縮します。因果エッジは `A -> B`、`A -x B`、任意の重みをサポートし、重複除去されます。
これらの証拠レベルと因果エッジは、モデルが提案した内容の構造化された記録であり、独立した統計エンジンが自動計算した結論ではありません。

### 5. 確信度のしきい値

システムは `HIGH` の確信度に対して次のヒューリスティックなしきい値を適用します。

- 明確な根本原因が存在する必要があり、`UNKNOWN` のままではいけません。
- `+` または `++` と評価された肯定的な証拠が少なくとも2つ必要です。
- `CONVERGE` 段階が高い確信度のしきい値を満たさない場合、`INTERVENE` に戻されます。

確信度の変化は履歴に保存されます。数ターンにわたって確信度が上がらない場合は `stuckTurns` が増え、ダッシュボードに停滞状態が表示されます。

## 4. 予測・介入・検証のループ

モデルが `Intervention` と予測を提案すると、システムは `pendingPrediction` を保存します。
ツールの実行後、モデルは検証結果を示す必要があります。保留中の予測は `Verdict` が解析された後にのみ終了します。

システムは、宣言されたコミットメントと実際のツール呼び出しが一致するかも確認します。

- モデルが介入を実行すると宣言したのにツールを呼び出さなかった場合、`no_tool_recovery` を記録して再実行を求めます。
- モデルがツール A を呼び出すと宣言したのに、実際にはツール B を呼び出した場合、`wrong_tool_recovery` を記録して再調整を求めます。
- 因果リカバリには有限の再試行予算があり、現在の実装では予算は3です。

つまり Entanglement は、モデルに分析を書かせるだけではありません。分析を検証可能なツール操作へ変換することを求めます。

## 5. Agent より優れている点

### 1. 未知の根本原因に適している

Agent は原因を推測してすぐに編集を開始することがあります。Entanglement は原因を仮説として保持し、どのように反証できるかの説明を求めます。

### 2. 複数ターンの調査に適している

現在の段階、証拠、却下された仮説、保留中の予測が次のターンのコンテキストに入り、会話が長くなっても調査の進捗を失いにくくします。

### 3. 間違った方向を見つけやすい

`BACKTRACK`、`rejected`、Kill Criterion、Lesson が連携して復帰経路を提供します。

### 4. 手動で監督しやすい

ダッシュボードはモデルの作業状態を段階、確信度、根本原因、証拠、補正記録にまとめます。そのため、モデルが堂々巡りをしているかを確認できます。

### 5. 成功事例を保存できる

高い確信度で収束した後、システムは `causal-case` メモリを書き込み、理論上は後で類似問題の経験として呼び出せます。

## 6. Agent より優れているとは限らない点

### 1. 明確なタスクでは遅い

状態解析、因果要約、検証プロトコルにより、単純な変更には不要な処理オーバーヘッドが加わります。

### 2. トークン消費が多い

各ターンで追加のモードコンテキスト、因果状態、証拠履歴、標準化された要約を送ります。

### 3. モデルが報告する情報に依存する

根本原因、証拠レベル、因果グラフは主にモデルが提案します。システムはそれらを解析、保存、表示し、限定的に補正するだけです。

### 4. プロトコルの誤判定が起こり得る

モデルが認識可能な因果フィールドを出力しない場合、システムが古い状態を再利用したり、確信度を下げたり、停滞ターンを増やしたり、リカバリを起動したりすることがあります。

### 5. 形式的な証明ではない

`HIGH` は、明確な根本原因と少なくとも2つの肯定的な証拠に基づくヒューリスティックな判断にすぎません。数学的証明や真の因果検証と同じではありません。

## 7. モードの選択

| タスクの種類 | 推奨モード | 理由 |
| --- | --- | --- |
| 明確な小規模変更、スタイル更新、単純なインターフェースフィールド | Agent | ツール機能で十分で、ワークフローが短くなります。 |
| 未知のバグ、リグレッション、モジュール横断の障害 | Entanglement | 仮説、証拠、介入、検証のループが必要です。 |
| 変更をまだ実行せずに解決策を分析する | Plan または Analyze | 直接的な変更と実行を減らせます。 |
| 複数の独立したモジュールを並列処理する | Agent Teams | 複数 AI の協調に特化したモードです。 |

## 8. 最終評価

「強力」をツール権限という意味で捉えるなら、Entanglement は概ね Agent と同等の能力を持ちます。複雑な問題における推論の整理、状態の継続性、検証という意味なら、Entanglement の方が強力です。
単純なタスクでの速度、トークン効率、直接実行という意味なら、通常の Agent の方が適しています。
したがって、最も正確な位置付けは次のとおりです。

> **Entanglement = Agent + 因果状態追跡 + 予測/介入/検証の制約 + 可視化 + 収束メモリ。**

Agent の完全な代替ではなく、複雑なデバッグと不確実な問題向けに設計された強化モードです。

## 9. 重要な注意

ユーザーインターフェースの「Causal Trace Complete」は、構造化された状態ブロックが解析されたことを示します。根本原因が独立して証明されたことを意味するものではありません。
