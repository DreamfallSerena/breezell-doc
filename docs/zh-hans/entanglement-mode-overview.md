# Entanglement 模式功能说明

> Entanglement 是面向复杂问题的因果推理增强模式。

## 摘要

Breezell 的“纠缠模式”不是量子算法，也不是自动启动多个模型的协作模式。
它的实际实现是“Agent 能力 + 因果状态机 + 预测/干预/验证约束 + 可视化面板 + 收敛记忆”。
它不会让底层模型突然变得更聪明，而是把复杂任务中的假设、证据、实验和结论持续保存并重新注入模型。

## 一、核心结论

纠缠模式不是 Agent 的完全替代品，而是面向复杂问题的状态化增强。

- **工具能力：** 纠缠模式继承 Agent 的文件、终端、搜索、MCP 和代码索引能力。
- **推理组织：** 纠缠模式额外维护阶段、根因、假设、证据、预测、验证和置信度。
- **执行效率：** 普通 Agent 对明确任务通常更快；纠缠模式会增加上下文和 Token 开销。
- **适用范围：** 未知 Bug、跨模块故障和需要实验验证的问题更适合纠缠模式。
- **能力边界：** 没有发现独立的纠缠模型、量子计算模块或默认的多模型并行执行路径。

## 二、实际工作原理

### 1. 模式选择

前端模式列表包含 `normal`、`plan`、`analyze`、`entanglement`、`agent` 和 `agent_teams`。
选择纠缠模式后，后续对话会启用因果状态追踪。

### 2. 继承 Agent 能力

后端模式判断会把 `entanglement` 映射到 Agent 类型，因此它可以继续调用文件工具、终端、搜索、MCP 和代码索引。
这也是它和只负责分析的模式的区别：纠缠模式仍然能够修改项目并执行验证。

### 3. 注入当前因果状态

每轮请求都会携带当前线程的因果状态，并使用 Agent 级别的活动文件、工作区和工具上下文。

### 4. 同一套模型和工具循环

纠缠模式和 Agent 使用相同的模型与工具执行能力。
因此它不等于 Agent Teams，也不会默认创建多个独立 AI；只有模型主动使用相关工具时，才可能产生额外的子任务或工具调用。

### 5. 模型回包解析

模型返回后，系统会解析阶段、根因、假设、证据、预测和验证结果，并将其保存到当前线程。
下一轮会继续使用这些状态；界面会把结构化状态块显示为 “Causal Trace Complete”。

### 6. 可视化与实时解析

纠缠面板组件 `G1` 会显示当前阶段、置信度、根因、假设、证据、因果图、修复、验证和系统纠偏。
模型流式输出期间，前端会按文本增长量或时间间隔重新解析状态；非 LLM 输出阶段则清理临时解析结果。

### 7. 收敛后的记忆

当状态进入高置信度的 `CONVERGE` 阶段并且存在明确根因时，系统会把本次问题整理成带有 `causal-case` 标签的 Memory Bank 节点。
记忆内容包括症状、根因、机制、决定性证据、修复、因果图、否决的假设和验证结果。

### 数据流

```text
下拉菜单选择 Entanglement
        ↓
全局设置 chatMode = "entanglement"
        ↓
读取当前线程 causalState
        ↓
注入因果上下文，仍使用普通 LLM/工具循环
        ↓
解析模型返回的阶段、假设、证据和验证结果
        ↓
写回线程状态并刷新仪表盘
        ↓
高置信度收敛后写入 causal-case 记忆
```

## 三、因果状态机

### 1. 阶段

| 阶段 | 实际含义 |
| --- | --- |
| `OBSERVE` | 收集现象和证据，根因尚未明确。 |
| `INTERVENE` | 已提出一个需要工具或实验验证的动作。 |
| `CONVERGE` | 根因、修复和验证逐渐闭环。 |
| `BACKTRACK` | 当前假设被否定，需要回退并重新判断。 |

### 2. 状态字段

线程中的核心状态包括：`phase`、`rootCause`、`mechanism`、`confidence`、`hypotheses`、`evidenceLog`、`evidenceSummary`、`causalGraph`、`causalGraphEdges`、`counterfactual`、`fix`、`verify`、`pendingPrediction`、`turnCount`、`stuckTurns` 和 `corrections`。

### 3. 假设管理

假设使用 `H1`、`H2` 等标识，并记录 `testing`、`confirmed` 或 `rejected` 状态。
同时保存 Kill Criterion、Lesson、创建回合和最近触碰回合，用于防止已经否定的思路被重复采用。

### 4. 证据和因果图

证据支持 `++`、`+`、`~`、`-`、`--` 五个等级，也可以记录证据来源工具。
解析器会保留最近 20 条详细证据，更早内容压缩成摘要；因果边支持 `A -> B`、`A -x B` 和可选权重，并会去重。
这些证据等级和因果边是模型提出内容的结构化记录，不是独立统计引擎自动计算出的结论。

### 5. 置信度门槛

系统对 `HIGH` 置信度设置了启发式门槛：

- 必须存在明确根因，不能仍然是 UNKNOWN。
- 至少需要两条 `+` 或 `++` 的正向证据。
- `CONVERGE` 阶段没有满足高置信度时，会被降回 `INTERVENE`。

置信度变化会保存历史；如果多轮没有上升，`stuckTurns` 会增加，仪表盘会显示停滞状态。

## 四、预测—干预—验证闭环

当模型提出 `Intervention` 和预测时，系统会保存 `pendingPrediction`。
工具执行之后，模型需要给出验证结果；解析到 `Verdict` 后，待验证预测才会关闭。

系统还会检查承诺和实际工具调用是否一致：

- 模型声明要执行干预但没有调用工具时，记录 `no_tool_recovery` 并要求重新执行。
- 模型声明调用工具 A、实际调用工具 B 时，记录 `wrong_tool_recovery` 并要求重新对齐。
- 因果恢复有有限次数预算，当前实现中的预算值为 3。

这使纠缠模式不只是让模型写一段分析，而是要求模型把分析转换成可验证的工具动作。

## 五、它比 Agent 强在哪里

### 1. 更适合未知根因

Agent 可能直接猜测一个原因并开始修改；纠缠模式会把原因保留为假设，并要求说明如何证伪。

### 2. 更适合多回合排查

当前阶段、证据、已否定假设和待验证预测会进入下一轮上下文，减少因聊天过长而丢失调查进度。

### 3. 更容易发现错误方向

`BACKTRACK`、`rejected`、Kill Criterion 和 Lesson 共同提供了回退机制。

### 4. 更容易人工监督

仪表盘将模型的工作状态压缩成阶段、置信度、根因、证据和纠偏记录，用户可以及时发现模型是否在原地打转。

### 5. 能沉淀成功案例

高置信度收敛后会写入 `causal-case` 记忆，后续理论上可以用于类似问题的经验召回。

## 六、它不一定比 Agent 强的地方

### 1. 明确任务上更慢

增加状态解析、因果摘要和验证协议后，简单改动会承担不必要的流程开销。

### 2. Token 消耗更高

每轮会额外携带模式上下文、因果状态、证据历史和标准化摘要。

### 3. 仍然依赖模型自报

根因、证据等级和因果图主要由模型提出，系统只负责解析、保存、展示和有限纠偏。

### 4. 可能出现协议误判

如果模型没有输出可识别的因果字段，系统可能沿用旧状态、降低置信度、增加停滞次数或触发恢复。

### 5. 不是形式化证明

`HIGH` 只是“明确根因 + 至少两条正向证据”的启发式判断，不能等同于数学证明或真实因果验证。

## 七、与其他模式的选择建议

| 任务类型 | 推荐模式 | 原因 |
| --- | --- | --- |
| 明确的小改动、样式修改、简单接口字段 | Agent | 工具能力足够，流程更短。 |
| 未知 Bug、回归问题、跨模块故障 | Entanglement | 需要假设、证据、干预和验证闭环。 |
| 只分析方案、暂不执行修改 | Plan 或 Analyze | 减少直接修改和执行。 |
| 多个独立模块需要并行处理 | Agent Teams | 这是专门的多 AI 协作模式。 |

## 八、最终判断

如果“强大”指工具权限，纠缠模式基本不弱于 Agent；如果“强大”指复杂问题的推理组织、状态连续性和验证能力，纠缠模式更强。
如果“强大”指简单任务的速度、Token 效率和直接执行能力，普通 Agent 更合适。
因此最准确的定位是：

> **Entanglement = Agent + 因果状态追踪 + 预测/干预/验证约束 + 可视化 + 收敛记忆。**

它不是 Agent 的全面替代品，而是为复杂调试和不确定问题设计的增强模式。

## 九、重要说明

用户界面中的 “Causal Trace Complete” 表示结构化状态块已被解析，不表示根因已经被独立证明。
