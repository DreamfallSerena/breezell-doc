# Breezell 与 DSH：最根本的区别是什么？

我们最近经常收到一个问题：Breezell 与 DSH（deepseek-harness）到底有什么不同？简单来说，两者采用了不同的开发与维护模式，也因此形成了不同的产品取向。

## 快速对比

| 对比维度 | DSH | Breezell |
| --- | --- | --- |
| 产品模式 | 社区驱动的框架与生态 | 主要由官方团队维护的一体化 IDE |
| 核心体验 | 由基础框架与用户选择的社区扩展共同组成 | 默认提供可直接使用的完整产品体验 |
| 功能维护 | 功能和集成可能较多依赖社区贡献者 | 核心功能、集成与产品行为由官方统一协调 |
| 扩展能力 | 自由度高，便于快速实验 | 目前更受控，正在逐步开放 |
| 一致性 | 不同扩展之间的体验和质量可能存在差异 | 产品行为、设计和发布标准更加统一 |
| 安全边界 | 很大程度取决于扩展来源、权限和实现方式 | 官方核心维持在更可控的安全边界内 |
| 主要取舍 | 灵活性更高，同时需要用户认真审查扩展 | 控制力更强，但修复和功能可能需要等待官方开发 |

## DSH 的模式

DSH 更接近一个由社区驱动的框架。官方项目主要提供底层基础并展示可以在其上构建什么，而许多实际功能、集成、插件和工作流选择可能来自社区扩展。

这种模式拥有很高的自由度，用户可以快速实验并组合高度定制的开发环境。但自由度越高，用户承担的审查责任也越大。与任何可扩展开发工具一样，来源不可信或设计不完善的扩展，可能带来凭据泄露、提示词注入入口、行为不一致、运行不稳定，甚至破坏性操作等风险。

实际风险取决于扩展来源、申请权限、实现质量和审查机制，而不能简单地由“是否为社区开发”来判断。

## Breezell 的模式

Breezell 主要作为官方产品进行开发、集成和维护。我们的目标是让大多数用户无需自行拼装核心工作流，安装后即可获得完整、稳定的使用体验。

这种模式让 Breezell 可以统一协调产品行为、界面设计、模型与工具集成、兼容性测试、安全边界、更新和支持。

只要用户不主动安装来源不可信的第三方扩展，Breezell 的核心体验就会保持在官方维护的环境中，从而显著降低未知扩展代码、凭据处理、提示词注入和破坏性行为带来的不确定性。

::: info 安全边界不等于绝对安全
安装第三方扩展前，仍应检查其来源、发布者、权限范围和信誉。
:::

## 这种模式的取舍

官方统一维护能够提高一致性、稳定性和可控性，但也会形成开发资源瓶颈。Breezell 当前更加依赖官方团队，因此部分问题修复、模型集成和新功能需要等待我们直接处理。

高度社区化的生态通常可以更快地试验和扩张。Breezell 目前牺牲了一部分开放速度，以换取更可预测的核心产品体验。

## Breezell 的发展方向

Breezell 基于 VS Code 构建，并持续跟进 VS Code 更新，因此已经具备发展成熟扩展生态的技术基础。

我们的长期方向是允许社区创建和分发扩展，同时保留清晰的权限声明、相互隔离的安全边界、透明可追踪的扩展来源、稳定的官方 API，以及不依赖第三方插件也能正常使用的官方核心。

## 总结

> **DSH 更接近一个追求最大自由度的社区驱动框架；Breezell 则更重视提供完整、由官方持续维护的产品，在一致性、稳定性和安全边界方面投入更多，并以受控方式逐步开放扩展能力。**

产品理念与维护模式的差异，就是 Breezell 和 DSH 之间最根本的区别。
