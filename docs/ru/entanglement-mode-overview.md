# Обзор режима Entanglement

> Entanglement — режим усиления причинно-следственного рассуждения для сложных задач.

## Краткое описание

Режим Entanglement в Breezell — не квантовый алгоритм и не режим совместной работы, который автоматически запускает несколько моделей.
Его реализация объединяет возможности Agent, машину причинных состояний, ограничения прогнозирования/вмешательства/проверки, панель визуализации и память после сходимости.
Он не делает базовую модель внезапно умнее. Вместо этого он постоянно сохраняет и заново передаёт модели гипотезы, доказательства, эксперименты и выводы, связанные со сложными задачами.

## 1. Основные выводы

Entanglement не является полной заменой Agent. Это состояние-ориентированное усиление для сложных задач.

- **Возможности инструментов:** Entanglement наследует возможности Agent для работы с файлами, терминалом, поиском, MCP и индексом кода.
- **Организация рассуждений:** Entanglement дополнительно поддерживает этапы, первопричины, гипотезы, доказательства, прогнозы, проверки и уровень уверенности.
- **Эффективность выполнения:** Для чётко определённых задач обычный Agent обычно быстрее; Entanglement увеличивает расход контекста и токенов.
- **Лучшее применение:** Entanglement лучше подходит для неизвестных ошибок, сбоев между модулями и задач, требующих экспериментальной проверки.
- **Границы возможностей:** Отдельной модели Entanglement, модуля квантовых вычислений или стандартного пути параллельного выполнения несколькими моделями нет.

## 2. Как это работает

### 1. Выбор режима

Список режимов во frontend включает `normal`, `plan`, `analyze`, `entanglement`, `agent` и `agent_teams`.
После выбора Entanglement в следующих ходах разговора включается отслеживание причинного состояния.

### 2. Наследование возможностей Agent

Определение режима на backend сопоставляет `entanglement` с типом Agent, поэтому режим может продолжать вызывать инструменты файлов, терминал, поиск, MCP и индекс кода.
Это также отличает его от режимов только для анализа: Entanglement по-прежнему может изменять проект и выполнять проверку.

### 3. Внедрение текущего причинного состояния

Каждый запрос передаёт текущее причинное состояние потока и использует контекст активных файлов, рабочего пространства и инструментов уровня Agent.

### 4. Тот же цикл модели и инструментов

Entanglement и Agent используют одинаковые возможности модели и выполнения инструментов.
Поэтому Entanglement не равен Agent Teams и по умолчанию не создаёт несколько независимых ИИ. Дополнительные подзадачи или вызовы инструментов появляются только тогда, когда модель сама активно использует соответствующие инструменты.

### 5. Разбор ответа модели

После ответа модели система разбирает этап, первопричину, гипотезы, доказательства, прогнозы и результаты проверки, а затем сохраняет их в текущем потоке.
Следующий ход продолжает использовать это состояние; интерфейс показывает структурированный блок состояния как «Causal Trace Complete».

### 6. Визуализация и разбор в реальном времени

Компонент панели Entanglement `G1` отображает текущий этап, уверенность, первопричину, гипотезы, доказательства, причинный граф, исправление, проверку и системные коррекции.
Во время потокового вывода модели frontend повторно разбирает состояние по мере роста текста или через заданные интервалы. На этапах вывода без LLM временные результаты разбора очищаются.

### 7. Память после сходимости

Когда состояние достигает этапа `CONVERGE` с высокой уверенностью и существует ясная первопричина, система оформляет проблему в узел Memory Bank с тегом `causal-case`.
Память включает симптомы, первопричину, механизм, решающие доказательства, исправление, причинный граф, отклонённые гипотезы и результаты проверки.

### Поток данных

```text
Выбрать Entanglement в меню режимов

```

## 3. Машина причинных состояний

### 1. Этапы

| Этап | Значение |
| --- | --- |
| `OBSERVE` | Собирать явления и доказательства, пока первопричина ещё не ясна. |
| `INTERVENE` | Предложить действие, для проверки которого нужен инструмент или эксперимент. |
| `CONVERGE` | Постепенно замкнуть цикл между первопричиной, исправлением и проверкой. |
| `BACKTRACK` | Текущая гипотеза отклонена, и рассуждение должно вернуться к предыдущей точке. |

### 2. Поля состояния

Основное состояние потока включает `phase`, `rootCause`, `mechanism`, `confidence`, `hypotheses`, `evidenceLog`, `evidenceSummary`, `causalGraph`, `causalGraphEdges`, `counterfactual`, `fix`, `verify`, `pendingPrediction`, `turnCount`, `stuckTurns` и `corrections`.

### 3. Управление гипотезами

Гипотезы используют идентификаторы `H1`, `H2` и другие, а также записывают состояние `testing`, `confirmed` или `rejected`.
Система также сохраняет Kill Criterion, Lesson, ход создания и последний ход, в котором гипотеза затрагивалась, чтобы не принимать снова уже отклонённое рассуждение.

### 4. Доказательства и причинные графы

Для доказательств поддерживаются пять уровней: `++`, `+`, `~`, `-` и `--`. Можно также сохранить инструмент-источник доказательства.
Парсер сохраняет 20 последних подробных доказательств, а более раннее содержимое сжимает в сводку. Причинные рёбра поддерживают `A -> B`, `A -x B` и необязательные веса, а также удаление дубликатов.
Эти уровни доказательств и причинные рёбра являются структурированными записями содержимого, предложенного моделью, а не выводами, автоматически рассчитанными независимым статистическим движком.

### 5. Порог уверенности

Система применяет к уверенности `HIGH` следующий эвристический порог:

- Должна существовать ясная первопричина; состояние не может оставаться `UNKNOWN`.
- Требуются как минимум два положительных доказательства с оценкой `+` или `++`.
- Если этап `CONVERGE` не достигает порога высокой уверенности, он понижается до `INTERVENE`.

Изменения уверенности сохраняются в истории. Если уверенность не повышается несколько ходов подряд, увеличивается `stuckTurns`, а панель показывает состояние застоя.

## 4. Цикл прогнозирования, вмешательства и проверки

Когда модель предлагает `Intervention` и прогноз, система сохраняет `pendingPrediction`.
После выполнения инструмента модель должна предоставить результат проверки. Ожидающий прогноз закрывается только после разбора `Verdict`.

Система также проверяет, соответствует ли заявленное обещание фактическому вызову инструмента:

- Если модель заявляет, что выполнит вмешательство, но не вызывает инструмент, система записывает `no_tool_recovery` и запрашивает повторное выполнение.
- Если модель заявляет вызов инструмента A, но фактически вызывает инструмент B, система записывает `wrong_tool_recovery` и запрашивает выравнивание.
- Для причинного восстановления предусмотрен ограниченный бюджет повторных попыток; текущая реализация использует бюджет 3.

Таким образом, Entanglement не просто просит модель написать анализ: он требует превратить анализ в проверяемые действия инструментов.

## 5. В чём он сильнее Agent

### 1. Лучше подходит для неизвестных первопричин

Agent может угадать причину и сразу начать редактирование. Entanglement сохраняет причину как гипотезу и требует объяснить, как её можно опровергнуть.

### 2. Лучше подходит для многоходового исследования

Текущий этап, доказательства, отклонённые гипотезы и ожидающие прогнозы попадают в контекст следующего хода, снижая вероятность потери прогресса исследования по мере роста разговора.

### 3. Лучше обнаруживает неверное направление

`BACKTRACK`, `rejected`, Kill Criterion и Lesson вместе создают путь восстановления.

### 4. Проще контролировать вручную

Панель сжимает рабочее состояние модели до этапов, уверенности, первопричины, доказательств и записей коррекций, поэтому пользователь может заметить, что модель ходит по кругу.

### 5. Позволяет сохранять успешные случаи

После сходимости с высокой уверенностью система записывает память `causal-case`, которую теоретически можно позднее вызвать как опыт для похожих проблем.

## 6. В чём он не обязательно сильнее Agent

### 1. Медленнее для чётко определённых задач

Разбор состояний, причинные сводки и протокол проверки добавляют накладные расходы, не нужные для простых изменений.

### 2. Больше расход токенов

Каждый ход содержит дополнительный контекст режима, причинное состояние, историю доказательств и стандартизированные сводки.

### 3. Всё ещё зависит от данных, сообщаемых моделью

Первопричину, уровни доказательств и причинный граф в основном предлагает модель. Система только разбирает, сохраняет, показывает и ограниченно исправляет их.

### 4. Возможна ошибочная классификация протокола

Если модель не выводит распознаваемые причинные поля, система может использовать старое состояние, снизить уверенность, увеличить число застоявшихся ходов или запустить восстановление.

### 5. Это не формальное доказательство

`HIGH` — лишь эвристическое суждение на основе ясной первопричины и как минимум двух положительных доказательств. Оно не равно математическому доказательству или настоящей причинной проверке.

## 7. Выбор режима

| Тип задачи | Рекомендуемый режим | Причина |
| --- | --- | --- |
| Небольшие ясные изменения, обновления стиля или простые поля интерфейса | Agent | Его инструментов достаточно, а рабочий процесс короче. |
| Неизвестные ошибки, регрессии или сбои между модулями | Entanglement | Нужен замкнутый цикл гипотез, доказательств, вмешательства и проверки. |
| Анализ решения без выполнения изменений | Plan или Analyze | Уменьшает прямое изменение и выполнение. |
| Параллельная обработка нескольких независимых модулей | Agent Teams | Это специальный режим совместной работы нескольких ИИ. |

## 8. Итоговая оценка

Если под «мощностью» понимать разрешения инструментов, Entanglement в целом сопоставим с Agent. Если речь идёт об организации рассуждений, непрерывности состояния и проверке сложных задач, Entanglement сильнее.
Если важны скорость, экономия токенов и прямое выполнение простых задач, обычный Agent подходит лучше.
Наиболее точное описание выглядит так:

> **Entanglement = Agent + отслеживание причинного состояния + ограничения прогнозирования/вмешательства/проверки + визуализация + память после сходимости.**

Это не полная замена Agent, а усиленный режим для сложной отладки и неопределённых задач.

## 9. Важное примечание

«Causal Trace Complete» в интерфейсе означает, что структурированный блок состояния разобран. Это не означает, что первопричина доказана независимо.
