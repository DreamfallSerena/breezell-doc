# Breezell 與 DSH：最根本的差異是什麼？

我們最近經常收到一個問題：Breezell 與 DSH（deepseek-harness）究竟有什麼不同？簡單來說，兩者採用了不同的開發與維護模式，也因此形成不同的產品取向。

## 快速比較

| 比較面向 | DSH | Breezell |
| --- | --- | --- |
| 產品模式 | 社群驅動的框架與生態 | 主要由官方團隊維護的一體化 IDE |
| 核心體驗 | 由基礎框架與使用者選擇的社群擴充功能共同組成 | 預設提供可直接使用的完整產品體驗 |
| 功能維護 | 功能和整合可能較多依賴社群貢獻者 | 核心功能、整合與產品行為由官方統一協調 |
| 擴充能力 | 自由度高，方便快速實驗 | 目前更受控，正在逐步開放 |
| 一致性 | 不同擴充功能之間的體驗和品質可能存在差異 | 產品行為、設計和發布標準更加統一 |
| 安全邊界 | 很大程度取決於擴充來源、權限和實作方式 | 官方核心維持在更可控的安全邊界內 |
| 主要取捨 | 彈性更高，同時需要使用者仔細審查擴充功能 | 控制力更強，但修正和功能可能需要等待官方開發 |

## DSH 的模式

DSH 更接近一個由社群驅動的框架。官方專案主要提供底層基礎並展示可在其上建構的內容，而許多實際功能、整合、外掛程式和工作流程選擇可能來自社群擴充功能。

這種模式擁有很高的自由度，使用者可以快速實驗並組合高度自訂的開發環境。但自由度越高，使用者承擔的審查責任也越大。與任何可擴充開發工具一樣，來源不可信或設計不完善的擴充功能，可能帶來憑證外洩、提示詞注入入口、行為不一致、執行不穩定，甚至破壞性操作等風險。

實際風險取決於擴充來源、要求的權限、實作品質和審查機制，不能簡單地由「是否為社群開發」來判斷。

## Breezell 的模式

Breezell 主要作為官方產品進行開發、整合和維護。我們的目標是讓大多數使用者無需自行拼裝核心工作流程，安裝後即可獲得完整、穩定的使用體驗。

這種模式讓 Breezell 可以統一協調產品行為、介面設計、模型與工具整合、相容性測試、安全邊界、更新和支援。

只要使用者不主動安裝來源不可信的第三方擴充功能，Breezell 的核心體驗就會保持在官方維護的環境中，顯著降低未知擴充程式碼、憑證處理、提示詞注入和破壞性行為帶來的不確定性。

::: info 安全邊界不等於絕對安全
安裝第三方擴充功能前，仍應檢查其來源、發布者、權限範圍和信譽。
:::

## 這種模式的取捨

官方統一維護能夠提高一致性、穩定性和可控性，但也會形成開發資源瓶頸。Breezell 目前更加依賴官方團隊，因此部分問題修正、模型整合和新功能需要等待我們直接處理。

高度社群化的生態通常可以更快地試驗和擴張。Breezell 目前犧牲了一部分開放速度，以換取更可預測的核心產品體驗。

## Breezell 的發展方向

Breezell 基於 VS Code 建構，並持續跟進 VS Code 更新，因此已具備發展成熟擴充生態的技術基礎。

我們的長期方向是允許社群建立和分發擴充功能，同時保留清晰的權限聲明、相互隔離的安全邊界、透明可追蹤的擴充來源、穩定的官方 API，以及不依賴第三方外掛程式也能正常使用的官方核心。

## 總結

> **DSH 更接近一個追求最大自由度的社群驅動框架；Breezell 則更重視提供完整、由官方持續維護的產品，在一致性、穩定性和安全邊界方面投入更多，並以受控方式逐步開放擴充能力。**

產品理念與維護模式的差異，就是 Breezell 和 DSH 之間最根本的區別。
