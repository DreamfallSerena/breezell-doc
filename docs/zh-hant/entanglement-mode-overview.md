# Entanglement 模式功能說明

> Entanglement 是面向複雜問題的因果推理增強模式。

## 摘要

Breezell 的「糾纏模式」不是量子演算法，也不是自動啟動多個模型的協作模式。
它的實際實作是「Agent 能力 + 因果狀態機 + 預測/介入/驗證約束 + 視覺化面板 + 收斂記憶」。
它不會讓底層模型突然變得更聰明，而是持續保存複雜工作中的假設、證據、實驗和結論，並重新注入模型。

## 一、核心結論

糾纏模式不是 Agent 的完整替代品，而是面向複雜問題的狀態化增強。

- **工具能力：** 糾纏模式繼承 Agent 的檔案、終端機、搜尋、MCP 和程式碼索引能力。
- **推理組織：** 糾纏模式額外維護階段、根因、假設、證據、預測、驗證和信心度。
- **執行效率：** 一般 Agent 對明確工作通常更快；糾纏模式會增加內容和權杖開銷。
- **適用範圍：** 未知 Bug、跨模組故障和需要實驗驗證的問題更適合糾纏模式。
- **能力邊界：** 沒有發現獨立的糾纏模型、量子計算模組或預設的多模型平行執行路徑。

## 二、實際工作原理

### 1. 模式選擇

前端模式清單包含 `normal`、`plan`、`analyze`、`entanglement`、`agent` 和 `agent_teams`。
選擇糾纏模式後，後續對話會啟用因果狀態追蹤。

### 2. 繼承 Agent 能力

後端模式判斷會將 `entanglement` 對映到 Agent 類型，因此它可以繼續呼叫檔案工具、終端機、搜尋、MCP 和程式碼索引。
這也是它和只負責分析的模式之間的差異：糾纏模式仍然能夠修改專案並執行驗證。

### 3. 注入目前因果狀態

每回合請求都會攜帶目前執行緒的因果狀態，並使用 Agent 層級的活動檔案、工作區和工具內容。

### 4. 同一套模型和工具循環

糾纏模式和 Agent 使用相同的模型與工具執行能力。
因此它不等於 Agent Teams，也不會預設建立多個獨立 AI；只有模型主動使用相關工具時，才可能產生額外的子工作或工具呼叫。

### 5. 模型回應解析

模型回應後，系統會解析階段、根因、假設、證據、預測和驗證結果，並將它們儲存到目前執行緒。
下一回合會繼續使用這些狀態；介面會將結構化狀態區塊顯示為「Causal Trace Complete」。

### 6. 視覺化與即時解析

糾纏面板元件 `G1` 會顯示目前階段、信心度、根因、假設、證據、因果圖、修正、驗證和系統糾偏。
模型串流輸出期間，前端會依據文字增長量或時間間隔重新解析狀態；非 LLM 輸出階段則會清理暫時解析結果。

### 7. 收斂後的記憶

當狀態進入高信心度的 `CONVERGE` 階段並且存在明確根因時，系統會將這次問題整理成帶有 `causal-case` 標籤的 Memory Bank 節點。
記憶內容包括症狀、根因、機制、決定性證據、修正、因果圖、否決的假設和驗證結果。

### 資料流

```text
從下拉選單選擇 Entanglement
        ↓
設定全域 chatMode = "entanglement"
        ↓
讀取目前執行緒的 causalState
        ↓
注入因果內容，同時繼續使用標準 LLM/工具循環
        ↓
解析模型回傳的階段、假設、證據和驗證結果
        ↓
將狀態寫回執行緒並重新整理儀表板
        ↓
高信心度收斂後寫入 causal-case 記憶
```

## 三、因果狀態機

### 1. 階段

| 階段 | 實際含義 |
| --- | --- |
| `OBSERVE` | 收集現象和證據，根因尚未明確。 |
| `INTERVENE` | 已提出一個需要工具或實驗驗證的動作。 |
| `CONVERGE` | 根因、修正和驗證逐漸形成閉環。 |
| `BACKTRACK` | 目前假設被否定，需要回退並重新判斷。 |

### 2. 狀態欄位

執行緒中的核心狀態包括：`phase`、`rootCause`、`mechanism`、`confidence`、`hypotheses`、`evidenceLog`、`evidenceSummary`、`causalGraph`、`causalGraphEdges`、`counterfactual`、`fix`、`verify`、`pendingPrediction`、`turnCount`、`stuckTurns` 和 `corrections`。

### 3. 假設管理

假設使用 `H1`、`H2` 等識別碼，並記錄 `testing`、`confirmed` 或 `rejected` 狀態。
系統也會儲存 Kill Criterion、Lesson、建立回合和最近觸碰回合，以防止已被否定的思路再次採用。

### 4. 證據和因果圖

證據支援 `++`、`+`、`~`、`-`、`--` 五個等級，也可以記錄證據來源工具。
解析器會保留最近 20 條詳細證據，較早的內容會壓縮成摘要；因果邊支援 `A -> B`、`A -x B` 和可選權重，並會去重。
這些證據等級和因果邊是模型提出內容的結構化記錄，不是獨立統計引擎自動計算出的結論。

### 5. 信心度門檻

系統對 `HIGH` 信心度設定了啟發式門檻：

- 必須存在明確根因，不能仍然是 UNKNOWN。
- 至少需要兩條評為 `+` 或 `++` 的正向證據。
- `CONVERGE` 階段未達到高信心度門檻時，會降回 `INTERVENE`。

信心度變化會保存歷史；如果多個回合沒有上升，`stuckTurns` 會增加，儀表板會顯示停滯狀態。

## 四、預測—介入—驗證閉環

當模型提出 `Intervention` 和預測時，系統會儲存 `pendingPrediction`。
工具執行後，模型需要提供驗證結果；解析到 `Verdict` 後，待驗證預測才會關閉。

系統也會檢查承諾與實際工具呼叫是否一致：

- 模型宣告要執行介入但沒有呼叫工具時，記錄 `no_tool_recovery` 並要求重新執行。
- 模型宣告呼叫工具 A、實際呼叫工具 B 時，記錄 `wrong_tool_recovery` 並要求重新對齊。
- 因果恢復有有限次數預算，目前實作的預算值為 3。

這使糾纏模式不只是讓模型寫一段分析，而是要求模型將分析轉換成可驗證的工具動作。

## 五、它比 Agent 強在哪裡

### 1. 更適合未知根因

Agent 可能直接猜測一個原因並開始修改；糾纏模式會將原因保留為假設，並要求說明如何證偽。

### 2. 更適合多回合排查

目前階段、證據、已否定假設和待驗證預測會進入下一回合內容，降低因對話過長而遺失調查進度的機率。

### 3. 更容易發現錯誤方向

`BACKTRACK`、`rejected`、Kill Criterion 和 Lesson 共同提供回退路徑。

### 4. 更容易人工監督

儀表板將模型的工作狀態濃縮為階段、信心度、根因、證據和糾偏記錄，讓使用者能及時發現模型是否在原地打轉。

### 5. 能沉澱成功案例

高信心度收斂後會寫入 `causal-case` 記憶，理論上可在之後作為類似問題的經驗召回。

## 六、它不一定比 Agent 強的地方

### 1. 明確工作上更慢

加入狀態解析、因果摘要和驗證協定後，簡單變更會承擔不必要的流程開銷。

### 2. 權杖消耗更高

每回合會額外攜帶模式內容、因果狀態、證據歷史和標準化摘要。

### 3. 仍然依賴模型自我回報

根因、證據等級和因果圖主要由模型提出，系統只負責解析、儲存、顯示和有限糾偏。

### 4. 可能出現協定誤判

如果模型沒有輸出可識別的因果欄位，系統可能沿用舊狀態、降低信心度、增加停滯回合或觸發恢復。

### 5. 不是形式化證明

`HIGH` 只是「明確根因 + 至少兩條正向證據」的啟發式判斷，不能等同於數學證明或真實因果驗證。

## 七、與其他模式的選擇建議

| 工作類型 | 建議模式 | 原因 |
| --- | --- | --- |
| 明確的小型變更、樣式更新或簡單介面欄位 | Agent | 工具能力足夠，工作流程較短。 |
| 未知 Bug、回歸問題或跨模組故障 | Entanglement | 需要假設、證據、介入和驗證的閉環。 |
| 只分析方案、暫不執行變更 | Plan 或 Analyze | 減少直接修改和執行。 |
| 平行處理多個獨立模組 | Agent Teams | 這是專門的多 AI 協作模式。 |

## 八、最終判斷

如果「強大」指工具權限，糾纏模式大致不弱於 Agent；如果「強大」指複雜問題的推理組織、狀態連續性和驗證能力，糾纏模式更強。
如果「強大」指簡單工作的速度、權杖效率和直接執行能力，一般 Agent 更合適。
因此最準確的定位是：

> **Entanglement = Agent + 因果狀態追蹤 + 預測/介入/驗證約束 + 視覺化 + 收斂記憶。**

它不是 Agent 的全面替代品，而是為複雜偵錯和不確定問題設計的增強模式。

## 九、重要說明

使用者介面中的「Causal Trace Complete」表示結構化狀態區塊已被解析，不表示根因已經獨立獲得證明。
