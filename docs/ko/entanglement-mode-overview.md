# Entanglement 모드 개요

> Entanglement는 복잡한 문제를 위한 인과 추론 강화 모드입니다.

## 요약

Breezell의 Entanglement 모드는 양자 알고리즘도 아니고 여러 모델을 자동으로 실행하는 협업 모드도 아닙니다.
실제 구현은 Agent 기능, 인과 상태 머신, 예측/개입/검증 제약, 시각화 패널 및 수렴 메모리를 결합합니다.
기반 모델을 갑자기 더 똑똑하게 만드는 것이 아니라 복잡한 작업의 가설, 증거, 실험 및 결론을 지속적으로 보존하고 모델에 다시 주입합니다.

## 1. 핵심 결론

Entanglement는 Agent를 완전히 대체하지 않습니다. 복잡한 문제를 위한 상태 기반 강화 기능입니다.

- **도구 기능:** Entanglement는 Agent의 파일, 터미널, 검색, MCP 및 코드 인덱스 기능을 상속합니다.
- **추론 구성:** Entanglement는 단계, 근본 원인, 가설, 증거, 예측, 검증 및 신뢰도를 추가로 관리합니다.
- **실행 효율:** 명확하게 정의된 작업에서는 일반 Agent가 대체로 더 빠르며, Entanglement는 컨텍스트와 토큰 오버헤드를 추가합니다.
- **적합한 범위:** 알려지지 않은 버그, 모듈 간 장애 및 실험적 검증이 필요한 문제에는 Entanglement가 더 적합합니다.
- **기능 경계:** 별도의 Entanglement 모델, 양자 컴퓨팅 모듈 또는 여러 모델 간 병렬 실행을 위한 기본 경로는 없습니다.

## 2. 작동 방식

### 1. 모드 선택

프론트엔드 모드 목록에는 `normal`, `plan`, `analyze`, `entanglement`, `agent` 및 `agent_teams`가 포함됩니다.
Entanglement를 선택하면 이후 대화 턴에서 인과 상태 추적이 활성화됩니다.

### 2. Agent 기능 상속

백엔드 모드 확인은 `entanglement`를 Agent 유형으로 매핑하므로 파일 도구, 터미널, 검색, MCP 및 코드 인덱스를 계속 호출할 수 있습니다.
이 점이 분석 전용 모드와 다른 부분입니다. Entanglement는 여전히 프로젝트를 수정하고 검증을 실행할 수 있습니다.

### 3. 현재 인과 상태 주입

각 요청은 현재 스레드의 인과 상태를 전달하며 Agent 수준의 활성 파일, 워크스페이스 및 도구 컨텍스트를 사용합니다.

### 4. 동일한 모델 및 도구 루프

Entanglement와 Agent는 동일한 모델 및 도구 실행 기능을 사용합니다.
따라서 Agent Teams와 같지 않으며 기본적으로 여러 독립 AI를 생성하지도 않습니다. 모델이 관련 도구를 능동적으로 사용할 때만 추가 하위 작업이나 도구 호출이 발생할 수 있습니다.

### 5. 모델 응답 분석

모델이 응답하면 시스템은 단계, 근본 원인, 가설, 증거, 예측 및 검증 결과를 분석하여 현재 스레드에 저장합니다.
다음 턴에서도 이 상태를 계속 사용하며, 인터페이스는 구조화된 상태 블록을 “Causal Trace Complete”로 표시합니다.

### 6. 시각화 및 실시간 분석

Entanglement 패널 컴포넌트 `G1`은 현재 단계, 신뢰도, 근본 원인, 가설, 증거, 인과 그래프, 수정, 검증 및 시스템 보정을 표시합니다.
모델 스트리밍 출력 중 프론트엔드는 텍스트 증가량 또는 시간 간격에 따라 상태를 다시 분석합니다. LLM이 아닌 출력 단계에서는 임시 분석 결과를 정리합니다.

### 7. 수렴 후 메모리

상태가 높은 신뢰도의 `CONVERGE` 단계에 도달하고 명확한 근본 원인이 존재하면 시스템은 문제를 `causal-case` 태그가 붙은 Memory Bank 노드로 정리합니다.
메모리에는 증상, 근본 원인, 메커니즘, 결정적 증거, 수정, 인과 그래프, 거부된 가설 및 검증 결과가 포함됩니다.

### 데이터 흐름

```text
모드 메뉴에서 Entanglement 선택
        ↓
전역 chatMode = "entanglement" 설정
        ↓
현재 스레드의 causalState 읽기
        ↓
표준 LLM/도구 루프를 유지하면서 인과 컨텍스트 주입
        ↓
모델이 반환한 단계, 가설, 증거 및 검증 결과 분석
        ↓
상태를 스레드에 다시 기록하고 대시보드 새로 고침
        ↓
높은 신뢰도로 수렴한 후 causal-case 메모리 기록
```

## 3. 인과 상태 머신

### 1. 단계

| 단계 | 의미 |
| --- | --- |
| `OBSERVE` | 근본 원인이 아직 명확하지 않은 상태에서 현상과 증거를 수집합니다. |
| `INTERVENE` | 도구 또는 실험을 통한 검증이 필요한 작업을 제안합니다. |
| `CONVERGE` | 근본 원인, 수정 및 검증 사이의 루프를 점진적으로 닫습니다. |
| `BACKTRACK` | 현재 가설이 거부되었으며 추론을 이전 지점으로 되돌려야 합니다. |

### 2. 상태 필드

스레드의 핵심 상태에는 `phase`, `rootCause`, `mechanism`, `confidence`, `hypotheses`, `evidenceLog`, `evidenceSummary`, `causalGraph`, `causalGraphEdges`, `counterfactual`, `fix`, `verify`, `pendingPrediction`, `turnCount`, `stuckTurns` 및 `corrections`가 포함됩니다.

### 3. 가설 관리

가설은 `H1`, `H2`와 같은 식별자를 사용하며 `testing`, `confirmed` 또는 `rejected` 상태를 기록합니다.
또한 Kill Criterion, Lesson, 생성 턴 및 가장 최근에 다룬 턴을 저장하여 이미 거부된 추론이 다시 채택되지 않도록 합니다.

### 4. 증거 및 인과 그래프

증거는 `++`, `+`, `~`, `-` 및 `--`의 다섯 등급을 지원하며 증거의 출처 도구도 기록할 수 있습니다.
분석기는 가장 최근의 상세 증거 20개를 유지하고 이전 콘텐츠를 요약으로 압축합니다. 인과 간선은 `A -> B`, `A -x B` 및 선택적 가중치를 지원하며 중복을 제거합니다.
이러한 증거 등급과 인과 간선은 모델이 제안한 콘텐츠의 구조화된 기록이며 독립 통계 엔진이 자동 계산한 결론이 아닙니다.

### 5. 신뢰도 임계값

시스템은 `HIGH` 신뢰도에 다음 휴리스틱 임계값을 적용합니다.

- 명확한 근본 원인이 있어야 하며 `UNKNOWN`으로 남아서는 안 됩니다.
- `+` 또는 `++`로 평가된 긍정적 증거가 최소 두 개 필요합니다.
- `CONVERGE` 단계가 높은 신뢰도 임계값을 충족하지 못하면 `INTERVENE`로 낮아집니다.

신뢰도 변화는 기록에 보존됩니다. 여러 턴 동안 신뢰도가 증가하지 않으면 `stuckTurns`가 증가하고 대시보드에 정체 상태가 표시됩니다.

## 4. 예측-개입-검증 루프

모델이 `Intervention`과 예측을 제안하면 시스템은 `pendingPrediction`을 저장합니다.
도구가 실행된 후 모델은 검증 결과를 제공해야 합니다. `Verdict`가 분석된 후에만 대기 중인 예측이 종료됩니다.

시스템은 선언된 약속이 실제 도구 호출과 일치하는지도 확인합니다.

- 모델이 개입을 수행하겠다고 했지만 도구를 호출하지 않으면 `no_tool_recovery`를 기록하고 다시 실행하도록 요청합니다.
- 모델이 도구 A를 호출하겠다고 했지만 실제로 도구 B를 호출하면 `wrong_tool_recovery`를 기록하고 재정렬을 요청합니다.
- 인과 복구에는 제한된 재시도 예산이 있으며 현재 구현의 예산은 3입니다.

이는 Entanglement가 모델에 분석을 작성하도록 요청하는 데 그치지 않고 분석을 검증 가능한 도구 작업으로 변환하도록 요구한다는 뜻입니다.

## 5. Agent보다 강한 점

### 1. 알려지지 않은 근본 원인에 더 적합

Agent는 원인을 추측하고 즉시 편집을 시작할 수 있습니다. Entanglement는 원인을 가설로 유지하고 어떻게 반증할 수 있는지 설명하도록 요구합니다.

### 2. 여러 턴의 조사에 더 적합

현재 단계, 증거, 거부된 가설 및 대기 중인 예측이 다음 턴의 컨텍스트에 포함되어 대화가 길어져도 조사 진행 상황을 잃을 가능성을 줄입니다.

### 3. 잘못된 방향을 더 쉽게 발견

`BACKTRACK`, `rejected`, Kill Criterion 및 Lesson이 함께 복구 경로를 제공합니다.

### 4. 수동 감독이 더 쉬움

대시보드는 모델의 작업 상태를 단계, 신뢰도, 근본 원인, 증거 및 보정 기록으로 요약하므로 모델이 같은 곳을 맴도는지 확인할 수 있습니다.

### 5. 성공 사례를 보존할 수 있음

높은 신뢰도로 수렴한 후 시스템은 `causal-case` 메모리를 기록하며, 이 메모리는 이론적으로 나중에 유사한 문제의 경험으로 불러올 수 있습니다.

## 6. Agent보다 항상 강한 것은 아닌 점

### 1. 명확한 작업에는 더 느림

상태 분석, 인과 요약 및 검증 프로토콜은 간단한 변경에 불필요한 처리 오버헤드를 추가합니다.

### 2. 토큰 사용량이 더 많음

각 턴에 추가 모드 컨텍스트, 인과 상태, 증거 기록 및 표준화된 요약이 포함됩니다.

### 3. 여전히 모델이 보고한 정보에 의존

근본 원인, 증거 등급 및 인과 그래프는 주로 모델이 제안합니다. 시스템은 이를 분석하고 저장하고 표시하며 제한적으로 보정할 뿐입니다.

### 4. 프로토콜 오분류 가능

모델이 인식 가능한 인과 필드를 출력하지 않으면 시스템이 이전 상태를 재사용하거나 신뢰도를 낮추거나 정체 턴 수를 늘리거나 복구를 트리거할 수 있습니다.

### 5. 형식적 증명이 아님

`HIGH`는 명확한 근본 원인과 두 개 이상의 긍정적 증거를 바탕으로 한 휴리스틱 판단일 뿐입니다. 수학적 증명이나 실제 인과 검증과 같지 않습니다.

## 7. 모드 선택

| 작업 유형 | 권장 모드 | 이유 |
| --- | --- | --- |
| 명확한 소규모 변경, 스타일 업데이트 또는 단순한 인터페이스 필드 | Agent | 도구 기능으로 충분하며 워크플로가 더 짧습니다. |
| 알려지지 않은 버그, 회귀 또는 모듈 간 장애 | Entanglement | 가설, 증거, 개입 및 검증의 폐쇄 루프가 필요합니다. |
| 아직 변경을 실행하지 않고 해결책 분석 | Plan 또는 Analyze | 직접적인 수정과 실행을 줄입니다. |
| 여러 독립 모듈을 병렬로 처리 | Agent Teams | 여러 AI 협업을 위한 전용 모드입니다. |

## 8. 최종 평가

“강력하다”가 도구 권한을 의미한다면 Entanglement는 대체로 Agent와 같은 수준의 기능을 제공합니다. 복잡한 문제에서 추론 구성, 상태 연속성 및 검증을 의미한다면 Entanglement가 더 강력합니다.
간단한 작업에서 속도, 토큰 효율성 및 직접 실행을 의미한다면 일반 Agent가 더 적합합니다.
따라서 가장 정확한 설명은 다음과 같습니다.

> **Entanglement = Agent + 인과 상태 추적 + 예측/개입/검증 제약 + 시각화 + 수렴 메모리.**

Agent를 완전히 대체하는 것이 아니라 복잡한 디버깅과 불확실한 문제를 위해 설계된 강화 모드입니다.

## 9. 중요 참고 사항

사용자 인터페이스의 “Causal Trace Complete”는 구조화된 상태 블록이 분석되었다는 뜻입니다. 근본 원인이 독립적으로 증명되었다는 뜻은 아닙니다.
